Доклад по лабораторной работе №3

Тема: Интеграционное тестирование проектов и работа с тестовыми заглушками.


Для чего эта лаба вообще нужна
В лабораторных №1 и №2 мы проверяли отдельные функции в изоляции — это юнит-тесты. Проблема в том, что они не показывают, работает ли программа целиком, когда модули дёргают друг друга. Эта лаба как раз про это: собрать несколько классов в связанную систему и проверить, что она ведёт себя правильно на всём пути — от ввода пользователя до отправки данных наружу.

Второй смысл — научиться изолировать код от внешнего мира. Реальная программа не должна зависеть от того, есть ли под рукой база, живой email-сервер и человек за клавиатурой. Через unittest.mock мы подменяем всё это заглушками и тестируем логику, а не инфраструктуру.




Суть работы:

Нужно было сделать проект из пяти классов, которые взаимодействуют через контроллер, и написать на unittest минимум 5 тестов, из которых 3 — интеграционных. Обязательное условие: подменять пользовательский ввод и отправку данных через mock.


У меня вариант «Треугольник». Классы такие:


TriangleCalculator — чистая логика: по трём сторонам возвращает тип треугольника или текст ошибки. Достался в наследство от лабы №1.


Database — работа с SQLite. Три метода: add_record, get_record, delete_record. Ключ — три стороны, поля — тип и ошибка.


UserInterface (abc) + ConsoleUserInterface — абстрактный интерфейс и его реализация через input(). Абстракция нужна, чтобы контроллер не зависел от конкретного способа ввода.


EmailService (abc) + FakeEmailService — по той же схеме: абстракция + имитация отправки. По ТЗ реальную отправку делать не надо, только её заглушку.


Controller — связывает всё вместе. Спрашивает стороны у UI, лезет в БД, если записи нет — считает через калькулятор и сохраняет, если есть — берёт готовое. Потом шлёт строку через email-сервис и возвращает результат.


Плюс main_lab3.py — точка входа, чтобы можно было запустить руками.



Что проверяют тесты:

Пять тестов, три из них интеграционные.

Интеграционные прогоняют всю цепочку разом:

Новый треугольник — ввод 3, 4, 5, проверяем, что вернулся «Разносторонний», что запись появилась в БД и что email-сервис дёрнулся ровно один раз.

Треугольник уже в БД — запись лежит заранее, результат берётся из базы, а не пересчитывается.

Невалидный треугольник — ввод 1, 2, 5, проверяем, что вернулась ошибка, в БД легла запись с заполненным полем error, а email всё равно ушёл.

Юнит-тесты бьют по отдельным модулям:

CRUD по БД — добавили, нашли, удалили, не нашли.

Типы треугольников — по одной проверке на каждую ветку калькулятора.
